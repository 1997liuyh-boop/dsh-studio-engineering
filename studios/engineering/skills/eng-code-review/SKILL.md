# 评审改动

## 准备

1. 调用 `eng_graph` 的 `changes`（评审分支时带上 `base`，如 `main`）。它返回改动落在哪些符号上，以及这些符号的影响面。
2. 找到这批改动的依据：`docs/iterations/<slug>/iteration.md`、需求文档，或用户的口头要求。没有依据时先问清楚这批改动要达到什么目的。
3. 读完整的差异，不要只读摘要。

## 第一遍：是否符合要求

只回答一个问题：这批改动做的是不是被要求做的事，做全了没有。

- 逐条对照验收标准或方案步骤，标出已实现、未实现、实现得不一样的。
- 找出要求之外的改动：顺手的重构、无关的格式调整、没人要的新功能。
- 有迭代方案时调用 `eng_plan`（`stage=check`），它会列出未落地的改动、签名偏差和计划外的文件。

第一遍有问题就先报告，不必急着进入第二遍。

## 第二遍：代码质量

按下面的顺序看，越靠前越重要：

1. **正确性**：边界值、空值、并发、错误路径、资源释放。在脑子里用具体输入走一遍。
2. **波及范围**：对 `changes` 返回的直接依赖逐个看，签名、返回值或行为变了之后调用方是否还成立。改了导出的符号而调用方没动的，重点核对。
3. **测试**：新行为有没有测试；测试测的是行为还是在照抄实现；有没有被删掉或跳过的测试。
4. **可读性**：命名是否表达意图，有没有重复，有没有比需要的更复杂。
5. **一致性**：是否沿用了项目已有的写法、目录约定和注释语言。

## 给出意见

每条意见包含：文件与行号、问题是什么、会导致什么后果、建议怎么改。按严重程度分三级：

- **必须改**：会出错、丢数据、破坏现有功能，或没有达到要求。
- **建议改**：现在不出错，但会明显增加后续维护成本。
- **可选**：风格和偏好。数量多时只挑最有价值的几条。

没有把握的地方写成疑问，并说明你核对了什么、没核对什么。不要为了显得仔细而凑条数；没有问题就说没有发现问题，并说明看过哪些方面。

## 收到评审意见时

- 先确认理解了意见，再核对它在技术上是否成立：打开代码看，跑一下验证。
- 成立就改，改完验证。不成立就说明理由和证据。
- 不要没核实就全盘接受，也不要没核实就反驳。
