# 完成前验证

没有刚刚运行过的验证结果，就不要说任务完成。

## 每次下结论之前

1. **确定**：哪条命令或哪个检查能证明这个结论？
2. **运行**：完整地、重新地跑一遍。几分钟前的结果、上一轮的结果都不算。
3. **读完**：看完整输出和退出码，数一数失败和跳过的数量。
4. **对照**：输出支持这个结论吗？
   - 不支持：按实际状态汇报，附上输出。
   - 支持：给出结论，并说明依据。

## 什么才算证据

| 结论 | 需要的证据 | 不算证据 |
|---|---|---|
| 测试通过 | 刚跑的测试输出，失败数为 0 | 之前跑过、理论上应该通过 |
| 类型检查通过 | 类型检查命令退出码为 0 | 代码规范检查通过 |
| 构建成功 | 构建命令退出码为 0 | 类型检查通过 |
| 缺陷已修复 | 复现步骤不再触发问题 | 代码改了，看起来对 |
| 需求已完成 | 对照验收标准逐条核对 | 测试通过 |
| 回归测试有效 | 看到它先失败、修复后通过 | 只看到它通过 |

## 汇报的写法

- 说清楚验证了什么、怎么验证的、结果是什么。
- 没有验证的部分明确列出来，说明原因（没有环境、需要人工操作、需要真实数据）。
- 有失败就给出失败的输出，不要用「基本完成」「应该没问题」带过。
- 确实验证通过的，直接说通过，不必加多余的保留语气。

## 出现这些说法时，先去验证

「应该可以了」「看起来没问题」「大概率通过」「我有把握」「只是个小改动」。

把握不是证据。小改动同样会出错。

## 委托出去的工作

别的会话或子任务报告「已完成」时，那是它的说法。看一下实际的改动和验证输出，确认之后再向用户转述。
