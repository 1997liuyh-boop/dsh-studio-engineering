# 领域术语表

需求里叫「订单」，接口里叫 `trade`，页面上叫「交易记录」：三个词是不是同一个东西，决定了方案会不会改错地方。术语表把业务概念和代码里的名字对上。

## 什么时候做

- 读需求时发现一个概念有多个叫法，或一个词有多个含义。
- 要给新功能里的概念起名字。
- 新人（或新会话）反复问同一个词是什么意思。

不需要一次建全。遇到一个、理清一个、记一个。

## 步骤

1. **收集**。从需求文档、界面文案、接口字段、类型定义和数据库表名里找出核心名词。用 `eng_graph` 的 `search` 查每个词在代码里对应哪些类型、组件和接口。
2. **辨别**。对每个词确认：
   - 它的准确定义，一两句话。
   - 它与相近概念的区别（「订单」与「子订单」，「用户」与「账号」）。
   - 代码里现有的名字，以及有没有多个名字指同一个东西。
3. **定名**。每个概念选一个中文名和一个代码里的英文名。已有代码用法不一致时，以使用最多的那个为准，其余列为别名。拿不准的问用户，不要自己定业务含义。
4. **记录**。写到 `docs/glossary.md`（项目已有术语文档时写到那里）。

## 记录的格式

```markdown
## 订单（Order）

用户一次结算产生的记录，包含一件或多件商品。

- 代码：`types/order.ts#Order`、`server/api/orders/`
- 别名：交易（trade，仅旧接口字段使用，新代码不再使用）
- 区别：子订单（SubOrder）是订单按商家拆分后的部分，一个订单有一个或多个子订单。
```

## 使用

- 写方案和功能点时用术语表里的名字。
- 新增类型、函数、组件时按术语表命名。
- 发现现有代码的命名与术语表冲突：记进术语表的别名里，并向用户提出，是否重命名由用户决定。重命名是一次独立的改动，不要混在功能开发里。

## 不要做

- 不要把每个变量名都收进来。只收业务概念。
- 不要自行发明业务含义。定义来自需求方、产品文档或现有行为。
- 不要为了统一命名去改与当前任务无关的代码。
