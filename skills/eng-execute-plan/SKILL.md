# 按方案实现

## 开始之前

1. 读 `docs/iterations/<slug>/iteration.md` 全文。方案里有待确认项、或者你读完觉得某一步走不通，先提出来，不要边做边猜。
2. 看一眼工作区状态。有与本次无关的未提交改动时告诉用户，不要把它们混进来。
3. 按步骤建立任务清单。

## 每一步

1. 只做这一步列出的文件和内容。
2. 动手前读要改的符号和它的直接调用方。方案里的签名是设计，实际代码以读到的为准。
3. 这一步能先写测试的，先写测试并确认它失败，再写实现。
4. 执行方案写的验证方式，看实际输出。通过了再进入下一步。
5. 验证没通过：先找原因并修复；连续两次没修好，停下来报告现象、已经试过的做法和你的判断。

## 遇到这些情况要停下来

- 方案指向的文件或符号不存在，或签名和方案写的不一样。
- 按方案做会破坏方案没提到的现有功能。
- 需要改方案之外的文件才能继续。
- 验证方式本身跑不起来（缺依赖、缺环境）。

停下来时说清楚：卡在哪一步、看到了什么、有哪几种处理办法、你倾向哪一种。用户同意调整后，让方案与实际保持一致：重新用 `eng_plan`（`stage=submit`）提交修订后的方案。

## 全部做完之后

1. 调用 `eng_plan`（`stage=check`，带上 `slug`）。它会核对：每处改动是否落地、签名是否与设计一致、有没有计划外的改动、签名变化的直接调用方有没有跟着改。
2. `issues` 逐条解决；`warnings` 逐条判断，属于有意为之的在汇报里说明原因。
3. 跑项目自己的检查（类型检查、测试、代码规范）。
4. 汇报：完成了哪些步骤、验证结果、与方案不一致的地方、没有做或没有验证的部分。

## 不要做

- 不要跳过验证去赶下一步。
- 不要顺手重构方案之外的代码。
- 不要因为验证麻烦就改验证方式；确实要改时说明原因。
- 没有实际运行过的检查，不要说它通过了。
