# 系统化调试

没有找到根因之前不改代码。凭猜测打补丁通常会掩盖问题，还会带来新问题。

## 第一阶段：弄清现象

1. **完整读错误信息**。报错文本、调用栈、行号、错误码都读完，不要只看第一行。
2. **稳定复现**。写下触发步骤，确认每次都能出现。复现不了就继续收集信息，不要开始猜。
3. **看最近改了什么**。`git diff`、最近的提交、新装的依赖、改过的配置。用 `eng_graph` 的 `changes` 可以把改动对应到具体符号和它们的影响面。
4. **多层系统逐层取证**。问题跨多个环节（页面 → 接口 → 服务 → 数据库）时，在每一层的入口和出口记录实际数据，跑一次，看数据在哪一层开始不对。先定位到出问题的那一层，再深入。

## 第二阶段：对比

1. 在项目里找一个功能相近、工作正常的例子。
2. 逐项列出正常的与出问题的之间有什么不同，不放过看起来无关的差异。
3. 用到了某个库或模式时，完整读它的用法说明，不要扫一眼就套用。

## 第三阶段：假设与验证

1. 写下一个明确的假设：「我认为原因是 X，因为 Y」。
2. 用最小的改动验证它，一次只改一处。
3. 假设不成立：撤回这次改动，提出新假设。不要在失败的尝试上继续叠加修改。
4. 遇到不理解的地方就说不理解，去查，不要装作明白。

## 第四阶段：修复

1. 先写一个能复现问题的失败测试（项目没有测试框架时，写下可重复的手动验证步骤）。
2. 针对根因做一处修改。不顺带做其他改进。
3. 确认新测试通过、原有测试没有被破坏、最初的现象消失。
4. **连续三次修复都没成功，停下来。** 这通常说明对问题的理解或者设计本身有问题。向用户报告已经确认的事实、已经排除的假设和你的判断，一起决定方向。

## 出现这些念头时，回到第一阶段

- 「先随便改一下试试。」
- 「大概是这里的问题。」
- 「一次多改几处，省得来回跑。」
- 「先不写测试，手动点一下就行。」
- 「再试最后一次。」（已经试了两次以上）

## 汇报

说明根因是什么、证据是什么、改了哪里、怎么验证的。没有找到根因、只是让现象消失时，如实说明。
