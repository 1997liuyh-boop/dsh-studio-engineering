# 写迭代方案

方案的读者是之后去实现它的人（或另一个会话里的模型），他们没有你现在的上下文。方案要具体到：改哪个文件的哪个符号、改成什么签名、怎么验证。

## 步骤

1. **定位**。对每个功能点，用 `eng_graph` 找到它落在哪里：
   - `search`：按名字、路径或用途找符号。
   - `context`：看一个符号的签名、成员、谁在用它、它用了谁。
   - `file`：看一个文件里有哪些符号。
   找到之后打开源码读一遍，图谱告诉你在哪里，不替代读代码。
2. **看影响面**。对每个要修改或删除的现有符号调用 `eng_graph` 的 `impact`。直接依赖很多、风险为高时，优先考虑不改签名的做法：新增可选参数、新增函数、保留旧入口。
3. **设计接口**。按下面「参数与方法设计」的要求写出每处改动的签名。
4. **排步骤**。按依赖排序，每一步小到可以单独验证，写明涉及的文件和验证方式。先改被依赖的底层，再改调用方；能先写测试的步骤先写测试。
5. **提交**。调用 `eng_plan`（`stage=submit`），工具会对照图谱核对并生成 `docs/iterations/<slug>/iteration.md`。返回 `issues` 时逐条改正后重新提交，不要绕过去手写文档。

## 参数与方法设计

每处新增或签名有变化的函数、方法、组件都要给出：

- **签名**：完整的声明行，带参数类型和返回类型。
- **参数表**：名称、类型、是否必填、默认值、含义。布尔参数写清楚真假各代表什么。
- **返回值**：成功时返回什么，失败时是抛错还是返回空值。
- **组件**：Props、事件（名称与载荷）、插槽；用 `defineModel` 的双向绑定单独列出。
- **兼容性**：现有调用方是否需要改。需要改时，方案里要有对应的步骤。

设计时的取舍：

- 沿用项目已有的命名和参数顺序。先用 `search` 找同类函数或组件，照它们的写法来。
- 同一个组件在多端（如 Web 与 UniApp）都有实现时，Props、事件名和插槽名保持一致；做不到一致的地方在兼容性里写明原因。
- 新增参数优先做成可选并给默认值，让现有调用方不用改。
- 参数超过三四个、或有多个可选项时，改用一个选项对象。
- 不为「以后可能需要」预留参数。

## 步骤的粒度

好的步骤：

```
S2 订单列表接口支持按状态筛选
文件：server/api/orders.get.ts、server/utils/orderQuery.ts
做法：orderQuery 的 buildWhere 新增可选参数 status；接口读取 query.status，非法值返回 400。
验证：pnpm vitest run server/utils/orderQuery.test.ts；用 status=paid 请求接口，只返回已支付订单。
```

不好的步骤：「实现后端逻辑」「完善前端页面」。

## 自查

- 每个功能点都有验收标准、至少一处改动、至少一个步骤。
- 修改和删除的目标都是图谱里真实存在的符号，签名是从代码里读到的，不是凭印象写的。
- 每个步骤都有可以实际执行的验证方式。
- 没有想清楚的地方写进 `openQuestions`，不要用含糊的措辞带过。
