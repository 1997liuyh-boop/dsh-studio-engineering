# 模块与接口设计

一个模块的价值在于它替调用方藏起了多少复杂度。接口小而内部做了很多事的模块是深模块，值得有；接口几乎和实现一样复杂的模块是浅模块，只是把代码搬了个地方。

## 判断边界放在哪里

- **调用方需要知道多少才能用对？** 需要知道的越少越好。调用方必须了解内部顺序、内部状态或「先调 A 再调 B」的，边界画错了。
- **一个需求变化会波及几个模块？** 总是一起改的几个文件应该合并或重新划分。
- **这层抽象删掉会怎样？** 删掉后调用方只是多写一两行直白的代码，这层抽象就不该存在。
- 抽公共逻辑之前先等到出现第三处重复。两处相似的代码未必是同一件事。

用 `eng_graph` 辅助判断：`context` 看一个符号被哪些地方、以什么方式使用；`overview` 看模块之间的依赖方向。被很多模块依赖的符号改接口要格外谨慎。

## 设计函数与方法

- 名字说明它做什么，不说明它怎么做。
- 参数顺序沿用项目里同类函数的顺序；必填在前，可选在后。
- 参数多于三四个，或有多个可选项时，用一个选项对象，并给每个字段写清含义和默认值。
- 布尔参数容易在调用处读不懂。两个行为差别大时，拆成两个函数或改用有名字的选项。
- 定义好错误：哪些情况抛错、哪些返回空值，同一个模块内保持一致。尽量通过设计让错误不可能发生，而不是把处理推给每个调用方。
- 返回调用方需要的东西，不返回内部结构。

## 设计组件

- Props 是组件的接口，同样要小。能由组件内部决定的事不暴露成 Prop。
- 状态归属清楚：由父级控制的用双向绑定，纯内部的不外露。
- 事件名用动词，载荷给出调用方处理它所需的全部信息。
- 多端都有的同名组件，Props、事件名与插槽名保持一致，降低使用者的学习成本；实现可以不同，接口不要不同。
- 需要高度定制的部分用插槽，不要为每种定制加一个 Prop。

## 改现有接口

1. 先用 `eng_graph` 的 `impact` 看有多少使用方。
2. 优先选不破坏现有调用的做法：新增可选参数并给默认值、新增一个函数、让旧入口转调新实现。
3. 必须破坏时，把所有直接调用方的修改列进方案，一次改完，不留半新半旧的状态。
4. 旧入口保留多久、何时删除，写在方案里。

## 自查

- 能用一两句话向没看过实现的人说清这个接口怎么用。
- 调用处的代码读起来像在描述意图。
- 没有为假想的未来需求预留参数或扩展点。
